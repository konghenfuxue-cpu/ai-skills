# GitHub 项目首页整理

让首次访问者迅速找到项目用途、效果、下载与安装方法，以及反馈入口。完成实际文档修改，不只提出建议；不把页面整理扩成程序重构或发布任务。

## 事实与素材

定向读取 README、安装文档、许可证和近期验证记录；按需核对仓库简介、主页 URL、Issues 开关、Release 资产及正式/预览/草稿状态。复用已有有效证据，不为排版重跑业务测试。

区分源码包、安装包、离线依赖包和完整软件。下载承诺必须与真实资产一致；没有安装包就说明现有使用方式，不能把 Source code 当成一键安装包。库或 CLI 使用真实的包安装和调用入口，不硬套桌面软件下载流程。

复用现有真实截图，检查私人路径、账号、通知及未公开素材。优先选择代表公开版本的效果；个人定制图单独标注差异。不为普通 README 排版新建网站、安装框架或无必要地生成横幅。

## 默认首页结构

按项目类型调整，避免机械套版：

1. **标题与一句话用途**：用用户语言说明能得到什么。
2. **主要入口**：突出真实下载或安装入口，附教程、反馈、更新链接；徽章不要挤走行动入口。
3. **实际效果**：一张主图；日常界面和更多截图用 `<details>` 收起；比较时用两列表格，避免连续大图淹没安装说明。
4. **快速开始**：尽量三步，保留必需前提和预期结果。仍需手动向导就说明，不把复杂设置称为一键完成；长命令与高级步骤移入详细教程。
5. **功能与常见问题**：按用户用途归类；优先回答实际发生的下载选择、版本要求、空白状态、备份和恢复问题。
6. **近期更新与验证范围**：放在来源致谢之前，不堆到许可证后；列用户可感知变化，链接完整变化记录，不把文件检查当作完整运行验收。
7. **来源致谢与许可证**：保留上游署名和分发边界；并列介绍参考项目，不自行按时间排先后或改称原创。

README 的本地文件使用仓库相对路径；聊天中的本地文件链接使用绝对路径，两者不要混用。用 GitHub 支持的 Markdown、表格和 `<details>`，不依赖复杂 CSS。

## 简介、下载与反馈

- 简介用一至两句概括用途和交付方式，必要时说明主程序另装。主页 URL 可指向推荐下载或文档。不要默认改仓库名、可见性、分支或许可证。
- 有合适的非草稿正式发布时可用 `releases/latest`。全是预览版则链接具体预览或 Releases 列表，明确状态。只有 tags 不表示没上传资产：先查状态，不为首页显示效果擅自取消 Pre-release、移动标签或转正式。
- 反馈入口优先 `issues/new/choose`，同时链接已有 Issues，核对 Issues 已开启。任务包含新增反馈入口时可加简短中文报错模板：软件/安装包版本、安装方式、复现步骤、预期与实际、报错或截图。提醒遮住私人路径与凭据，不要求整个私人配置或业务数据。
- 发布新资产、转正式、推送、修改远端简介和代发 Issue 不由本 Skill 自动授权；遵循用户当前会话授权，不重复确认已经授权的同一步。文档修改不意味着需要重发安装包。

## 检查与交付

检查整篇，清除与当前资产矛盾的旧描述，如已经发布却仍写“尚无安装包”。保留仍适用的限制、用户署名和项目约定。

核对新增图片、文档链接、相对引用与真实下载目标；检查架构及安装前提。具备获准的页面查看工具时核对实际渲染，重点看首屏入口、图片和折叠；否则检查源文档与引用，说明没有浏览器视觉验收。

运行 `git diff --check`，只提交授权范围内的文件。同步后核对远端，不能把本地提交说成已发布。最终简述修改内容、位置、实际验证和限制。

新建或修改本 Skill 时，按 [固定案例](evals/cases.md) 审阅触发和边界；格式验证不等于新聊天自动触发或模型行为评测通过。
